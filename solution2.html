COVERLINK 01 · 어떻게 일하나

CoverLink가 일하는 방식 — 원본을 보고, 절차대로 일하고, 업무가 넓어집니다

기준 지식은 원본으로 관리하고, 에이전트는 정해진 절차로 일하며, 위키가 쌓일수록 업무가 넓어집니다.

01
SOURCE OF TRUTH (SOT)

원본을 봅니다

CoverLink는 위키를 원본(SOT)으로 두고, 에이전트는 그 원본에서 만들어집니다.

  • 개발 표준 · 업무 정의는 OKF 위키 한 곳에
  • 모든 에이전트가 같은 원본을 기준으로 일합니다
예개발 표준 위키 · 에이전트 위키

02
AGENT PLAYBOOK

절차대로 일합니다

  • 검증된 업무 워크플로우를 그대로 실행

01

표준화된 개발 방법론 — 누가 빌드해도 동일한 구조

  • 네이밍·레이어·LLM 호출·MCP 계약·스택 가이드 등 80여 건의 개발 표준 위키 참조
  • 골격(구조·설정·계약 테스트)은 표준 그대로, AI는 업무 로직과 테스트만 작성
  • 표준이 바뀌면 다음 빌드부터 모든 에이전트에 일괄 반영 — 개별 코드 리뷰로 맞출 필요가 없습니다
02

메타(표준 용어) 연계 — 항목명을 전사 표준으로 통일

문의→enq 고객명→custNm 주소→addr
  • 한글 항목명 → 메타시스템(MCP)의 표준 영문명. 영문명은 메타에서 조회해 그대로 적용
  • 미등록 용어는 (메타 미등록) 표시 후 승인 목록 등록
03

ARCHITECTURE 13 · 어떤 구조인가

브라우저에서 서비스, 워커까지 — 위키 원본은 GitLab에 보관합니다

CoverLink Conceptual Architecture. 브라우저 → 서비스(Spring Boot) → 워커가 격리 컨테이너에서 생성·검증하고, 위키 원본은 GitLab에 보관합니다.

ARCHITECTURE 14 · 위키는 어떻게 만들어지나

대화와 문서를 업무 위키로 만듭니다 — Wiki(OKF) Editor

A. 대화로 명세 작성 → 승인자 확정 · B. 첨부 문서를 범위 선택 후 3층 지식(설명서·개념·원문)으로 — 모두 GitLab 위키에 Commit.

ARCHITECTURE 15 · 소스는 어떻게 검증되나

위키에서 검증된 소스까지 — WIKI Agent Builder

업무 위키(무엇을)와 개발 위키(어떻게)를 입력으로 생성 Sand Box → 검증 러너 → 통과분만 build/<ID> Branch에 Commit합니다.

ARCHITECTURE 16 · 만들어진 에이전트는 어떻게 도나

입력 검증부터 응답까지 — 보험사 시스템은 MCP로 조회만 합니다

CoverLink Agent Workflow — 생성된 에이전트의 실행 흐름. 입력 검증 → 지식 검색 → MCP 조회 → LLM 판정 → 코드 규칙 → 응답 — 보험사 시스템은 그대로 두고 MCP로 조회만 합니다.
